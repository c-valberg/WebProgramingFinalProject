Final Project
Project Overview
Purpose
A web application is comprised of a diverse collection of technologies working together to provide a user with a unified service. Building a web application will demonstrate not only mastery of various web technologies, but also proficiency in using them together. 
Overview
For this project you will define, design, and implement a complete web application. You will work in a group of two or three students. This document describes the requirements for your final web application as well as your intermediate submissions.
Breadth Requirements
Your web application must do the following:
1.	Use CSS or a CSS-based toolkit like Bootstrap to style the content. The application screens should be responsive to different device screen sizes (e.g., mobile phone, tablet, desktop monitor). 
2.	Use client-side scripting (TypeScript) to create an interactive web application.
3.	Use server-side scripting (Python-Flask) and a database to present content.
4.	Allow the user to add and/or modify content stored in the database so it persists across browser sessions and across devices.
5.	Use Fetch for dynamic loading or updating some content on a page.
6.	Have login functionality with at least two types of users that have different privileges.
7.	Use some library, framework, or API not covered in class. Part of your project is to research possibilities for this component. It must be approved by the instructor!
As long as you meet these requirements, you have considerable freedom to build a web application that is of interest to you. While you are encouraged to use existing libraries and toolkits, your group should create something for your final product that is substantially different than what is provided by the existing resources. Your contributions should include both server-side and client-side scripting. You are permitted and encouraged to use AI assistance but are expected to fully understand your finished product and to take ownership of the design decisions and tradeoffs made, even if they were produced by an AI assistant.
Complexity and Quality Requirements
In addition to the general requirements listed above, your application should fulfill the sufficiently complex product requirements you propose, correctly implementing the features you list therein. This means that different groups will be spending more or less time on different sections of the breadth requirements as appropriate to creating their proposed web application.
•	Complexity: More complex applications require more work and will be rewarded with a higher score when completed successfully. I will evaluate the complexity during your project demo to give you guidance about how complex a project will be challenging but still reasonable to complete in the time we have. Projects that are insufficiently complex will have a maximum score that is below a 100%.
•	Quality: Quality encompasses user experience as well as professional appearance. Since this is not a graphic design class, the goal here is not an eye-popping design. However, you should avoid sloppy or inconsistent UI elements, hard-to-navigate websites, and color schemes that are hard to read or painful to the eyes. There will be opportunities for you to get feedback on the quality of your website during the development process, so you can make improvements as needed for the final project.
•	Presentation: Your project is presented clearly and in a professional manner. The purpose and usefulness of your project are clear, and the most interesting and complex features are explained clearly and concisely.

 Project Proposal
Due Friday, October 9th by 11:55 pm
Overview
Answer the following questions. They address how your project will satisfy the "General Requirements" in the main project description. Write in a formal style with paragraphs of complete sentences. There is no length requirement, but you must completely address each of these questions clearly and concisely. If you have any questions about the categories or what technology might best be used to do something, please stop by office hours.
1.	What is the purpose of your website?
2.	What are some of the primary user interactions that you will implement using TypeScript? (e.g., geolocation, drawing on a canvas, moving pieces on a board, ...)  Unless your website makes heavy use of Fetch this will need to be a more significant component than validating forms.
3.	What are the main kinds of information your website will retrieve from your database?
4.	What information in the database will a user be able to modify by interacting with your site?
5.	What content do you plan to dynamically load without the user refreshing a web page? Examples for this could be autocompletion suggestions for a text box, periodically updating some status indicator (e.g., state of a board), or a "widget" on your page that retrieves information after the main page is loaded, either from your database or from a public site (e.g., weather information).
6.	What are the two categories of users for your site? This is often an authenticated user and an anonymous one or a regular user and an admin. The important aspect is that they have different privileges on the web site. Describe what privileges the one group has that the other does not. It is not permissible that one of your two categories have no functional access to your website.
7.	What external library, framework, or API do you plan on using? This must be a technology we will not cover in class and must be approved by the instructor.
Submission
Submit your completed document as a docx or pdf file on D2L.

 Project Checkpoint
Due Thursday, November 5th by 11:55 pm
Overview
For this checkpoint, you will produce an intermediate stage of your final project displaying some of the functionality. For this checkpoint, you must have made substantial progress on at least three of your breadth requirements. You must also have made sufficient progress to be, in the estimation of the instructor, at least 40% of the way through your project.
For this stage of the app, you must present a meaningful interface with no obvious crashes, though you probably will not have all functionality implemented — it is fine for there to be buttons that don’t do anything, pages missing details, etc. It must, however, be possible to meaningfully interact with your app in order to accomplish some basic tasks.
As part of the submission for this checkpoint, you will be submitting a copy of the final project rubric which you have filled out explaining your progress and assigning points based on what percentage of the work in that category you have completed. To receive credit for a category, you must submit a copy of the rubric that explains how your app satisfies that portion.
Submission
•	A video (3–7 minutes) with voiceover showing off all of the features currently implemented. Your video should be uploaded to YouTube (though it may be unlisted) and you should submit a link to your video.
•	A copy of the source code used when recording your demo so I can test it
•	A completed rubric explaining how your project fulfills the requirements so far.
•	Peer evaluations (on separate individual submissions)

 User Testing Demonstration
Due Monday, December 7th by 2:00 pm
Overview
For this checkpoint, you must have a completed, working, and stable web application. It is expected that there may be a few known remaining bugs and perhaps a missing feature or two. Things that are not working should be few and far between. There is no submission requirement for this checkpoint. Instead, you must come to class prepared to run a version of your web application for peer user testing by another group in the class. You may face a significant deduction on your final project grade if you do not have a reasonably stable application for this day of testing. It is fine, and in fact preferable, if it is a separate branch of your project set aside specifically as stable for testing.


 
Final Product
Due Monday, December 14th by 11:55 pm
Overview
The final submission is due prior to the start of your exam on December 15th. At this stage, your original proposal must be fully developed. Your app should be of a stability and quality such that you would feel comfortable hosting it for actual users. You must be able to demonstrate implementation of all required functionality points, a clean UI, and a bug-free run on mobile and desktop.
Documentation
Project documentation is expected to be 600-1200 words in length and must include the following
1.	A summary of the application’s purpose, audience, and unique features
2.	Information on what each team member contributed to the project including which features were implemented with AI assistance.
3.	A table of weekly hours worked on the project by each team member
4.	A discussion of how each of the required pieces of functionality was implemented and why that implementation makes sense in the overall scheme of the application.
5.	The group’s appraisal of the application and the process, including the following:
a.	What went well?
b.	What unexpected challenges did you encounter?
c.	What does the application do well?
d.	What could use more work?
e.	What would future versions include?
Submission
•	A video (5 – 10 minutes) with voiceover showing off the most important aspects of your web application. Your video should be uploaded to YouTube (though it may be unlisted) and you should submit a link to your video. It must not be marked as “for kids”!
•	A copy of the source code of your final application
•	A link and an invitation to view your GitHub repository
•	A completed rubric explaining how your project fulfills the requirements.
•	Peer evaluations (on separate individual submissions)
